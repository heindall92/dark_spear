# Findings Entity + Disk Persistence for Evidence

Status: approved by user 2026-08-29, ready for implementation plan.

## Problem

Auditor's ReAct agent runs tools and logs steps, but there is no concept of a
"finding" — a vulnerability the operator can review, edit, and hand to a
client. External review (Cursor) flagged this directly: "hoy el trabajo no es
'decidir el siguiente nmap' — es tener hallazgos con evidencia defendible."
Everything currently lives in the browser's chat transcript (IndexedDB); the
JSON export is a raw step-by-step log, not a deliverable a security
consultant could show a client.

This is the first slice of the "Sub-proyecto 2" work raised in external
review. It intentionally does NOT build the HTML report generator, MITRE
ATT&CK tagging, domain playbooks, or a semantic (novelty-aware) axis ledger —
those are separate specs, listed under Non-goals.

## Non-goals

- **HTML/PDF report generation from findings** — separate spec, natural next
  piece once findings exist to generate from.
- **MITRE ATT&CK technique tagging** — separate spec/sub-project.
- **Domain-specific playbooks** (AD, local privesc, API) — separate spec.
- **Migrating steps/scope/axis-ledger off IndexedDB.** Only findings +
  their evidence move to disk. Steps, the active-engagement record, and the
  axis ledger stay exactly where they are today (IndexedDB, browser-owned) —
  they already work, and rewriting that flow is a separate, much larger
  change this spec deliberately avoids (YAGNI: solve the findings/evidence
  problem, not "re-architect all persistence").
- **Automatic finding detection/heuristics.** The LLM proposes findings the
  same way it proposes tool calls — via its own judgment in the ReAct loop.
  No rule-based auto-detection is added.

## Existing dead code being removed

`js/db.js` already has an unused IndexedDB `findings` object store
(`addFinding`/`getFindings`, shape `{engagementId, type, value,
sourceStepId, timestamp}`) from the original engine spec (2026-08-21). It is
never called by any current code path (no UI, no LLM contract references
it) and has a different shape than what this spec builds. It is removed as
part of this work — keeping two unrelated things both named "findings" in
the same project would be a standing source of confusion.

Removing an IndexedDB object store requires bumping `DB_VERSION` (currently
`1` → `2`) and calling `db.deleteObjectStore("findings")` inside
`onupgradeneeded` — IndexedDB does not remove stores automatically just
because the code stops referencing them.

## Data model

A **Finding**, owned entirely by `bridge.py` (same trust tier as
`CURRENT_SCOPE`/the key pool — server is the source of truth, browser only
displays/collects operator input):

```python
{
    "id": "f-1",                 # sequential per engagement, string for stable JSON keys
    "title": str,
    "asset": str,                # e.g. target/host/URL the finding applies to
    "severity": "Critical" | "High" | "Medium" | "Low" | "Info",
    "description": str,          # what it is + why it matters (impact folded in)
    "remediation": str,
    "evidence_step_ids": [int, ...],   # step IDs (from the browser's IndexedDB steps store) that prove this
    "evidence_hashes": [str, ...],     # sha256 hex digests — populated only once accepted
    "status": "proposed" | "accepted" | "rejected" | "edited",
    "created_at": float,          # time.time()
    "reviewed_at": float | None,
}
```

`status: "edited"` is set when the operator changes any field before
accepting — distinguishes "accepted as the LLM proposed it" from "accepted
after the operator corrected something," useful later for judging how much
the operator actually trusts raw LLM output.

## Disk layout

```
~/.auditor/engagements/<engagement_dir>/
    findings.json      # list of Finding objects, rewritten on every mutation
    evidence/
        <sha256>.txt    # raw stdout of one evidence-cited step, written at accept time
```

`<engagement_dir>` is generated by `bridge.py` inside `/engagement/start`,
not supplied by the client: `f"{sanitized_target}_{timestamp}"`, e.g.
`127.0.0.1_2026-08-29T14-30-05` (target sanitized to filesystem-safe
characters, timestamp to the second, no colons). Returned in
`/engagement/start`'s response body as `engagement_dir` so the browser can
display it (e.g. in the export) without needing to reconstruct it.

Evidence text does not live on the server otherwise — `bridge.py`'s
`audit_log()` deliberately excludes full stdout, and `/exec`'s response
returns output straight to the browser without retaining a copy. So:
**evidence text travels browser → bridge.py at accept time, not before.** A
`proposed` or `rejected` finding has no evidence files on disk yet — only
`evidence_step_ids` (integers, meaningless outside the browser's IndexedDB
until resolved). Only `accept` triggers the browser to look up each cited
step's `output` in IndexedDB and send it up for hashing + writing.

## Bridge-side endpoints (new, token-gated like every other state-changing POST)

- `POST /findings/propose` — body `{title, asset, severity, description,
  remediation, evidence_step_ids}` → validates required fields and that
  `severity` is one of the five allowed values, assigns the next `id`,
  status `"proposed"`, appends to the current engagement's `findings.json`
  (written immediately — survives a `bridge.py` restart, same as scope/keys).
  Returns the created Finding. `400` on missing/invalid fields (this is the
  validation failure that flows back to `js/agent.js` as a generic
  `agent_error`, per the LLM-contract section below — no special-casing).
- `POST /findings/list` — no body, returns all Findings for the current
  engagement (used by the review panel).
- `POST /findings/review` — body `{finding_id, action: "accept" | "reject"
  | "edit", edited_fields?: {title?, asset?, severity?, description?,
  remediation?}, evidence_texts?: [{step_id: int, output: str}]}`.
  - `"reject"`: sets `status: "rejected"`, `reviewed_at`. Finding is NOT
    deleted — stays in `findings.json` for the record (the operator can see
    later what the LLM proposed and why it was turned down).
  - `"edit"`: applies `edited_fields` (any subset), sets `status: "edited"`.
    Does not require `evidence_texts` — editing text is independent of
    accepting.
  - `"accept"`: writes each entry in `evidence_texts` to
    `evidence/<sha256(output)>.txt`, records the resulting hashes in
    `evidence_hashes`, sets `status: "accepted"`, `reviewed_at`. If
    `evidence_texts` doesn't cover every ID in `evidence_step_ids`, that's
    still accepted — partial evidence is allowed (400 only on truly
    malformed requests, not on incomplete evidence sets — the operator may
    not always have every cited step's raw text handy, and forcing full
    coverage is presumptuous of case-by-case need, not something the spec
    should enforce rigidly).

All three require `CURRENT_SCOPE is not None` (an active engagement),
mirroring `/exec`'s existing guard.

## LLM contract + `js/agent.js` flow

`js/ollama.js`'s `RESPONSE_CONTRACT` gains a third valid response shape,
alongside the existing tool-call and `done` shapes:

```
or, if you have gathered enough evidence to report a real vulnerability finding:
{"finding": {"title": "<short title>", "asset": "<host/url/target this applies to>",
  "severity": "Critical"|"High"|"Medium"|"Low"|"Info",
  "description": "<what it is and why it matters>",
  "remediation": "<how to fix it>",
  "evidence_step_ids": [<step ids from Recent history that prove this>]},
 "reasoning": "<why you're reporting this now>"}
```

`askAgent` in `js/ollama.js` gains a branch: if `parsed.finding` is present
(and neither `tool` nor `done`), return `{ finding: parsed.finding,
reasoning: parsed.reasoning ?? "" }`.

`js/agent.js`'s `runAgentLoop` gains a branch, checked alongside the
existing `if (decision.done)`:

```javascript
if (decision.finding) {
  const finding = await proposeFinding(decision.finding);   // new bridge_client.js call
  onFindingProposed(finding);                                 // new optional callback, UI marker only
  continue;   // does NOT go through addStep/axis-ledger — findings are not tool executions
}
```

This does not pause the loop — no confirmation gate, no
`onPauseForConfirmation`. The operator reviews proposed findings
asynchronously via the review panel (see UI section), independent of the
loop's pace. If `proposeFinding`'s request is rejected by the server (400,
missing/invalid field), that throws inside the `try` block already wrapping
`askAgent`'s call — it flows through the EXISTING generic-error path
(`consecutiveErrors += 1`, `agent_error` verdict, the standard 5-strike
`agent_stuck` abort) with zero new error-handling code, exactly like a
malformed JSON response does today.

## UI

- `#findings-btn` next to the phase bar: `"Hallazgos (pendientes: N)"`,
  where N is the live count of `status === "proposed"` findings. Opens
  `#findings-panel` (same hidden-by-default pattern as `#key-manage-panel`).
- Panel lists findings, `proposed` ones first, each as a card: title,
  severity badge, asset, description, remediation, and its
  `evidence_step_ids` rendered as clickable references that scroll the
  steps feed to that step (reuses existing step DOM elements — no new
  step-lookup infrastructure needed beyond scrolling into view).
- Each card has **Aceptar**, **Rechazar**, and inline-editable fields (the
  same card doubles as the edit UI — no separate edit modal). Editing a
  field and then clicking Aceptar sends both the edit and the accept in one
  `/findings/review` call with `action: "accept"` plus `edited_fields` set
  (server applies edits before finalizing accept — no need for two round
  trips).
- On **Aceptar**: browser reads each cited step's `output` from IndexedDB
  (new `getStepsByIds(db, stepIds)` in `js/db.js`, a thin wrapper querying
  the existing `steps` store by primary key) and includes it as
  `evidence_texts` in the `/findings/review` call.
- `js/main.js`'s feed gets a lightweight marker rendering for
  `onFindingProposed` — a small card (`💡 Hallazgo propuesto: <title>`,
  clickable to open the findings panel) inserted into `#steps-feed` at the
  point it was proposed, giving the operator visibility without leaving the
  main feed. This is NOT a `step` — it doesn't go through `renderStep` or
  IndexedDB's `steps` store, just a UI-only marker.

## Testing

No automated suite for this project — manual verification only:

- Propose a finding via a raw `/findings/propose` curl call, confirm it
  appears in `/findings/list` with `status: "proposed"` and that
  `findings.json` on disk reflects it immediately.
- Reject a finding, confirm `status: "rejected"`, confirm it's still present
  in `/findings/list` (not deleted).
- Edit a finding's title via `/findings/review` with `action: "edit"`,
  confirm the change persists and `status` becomes `"edited"`.
- Accept a finding with a fabricated `evidence_texts` entry, confirm
  `evidence/<sha256>.txt` is created with the exact content, and the hash in
  `findings.json` matches `sha256sum` of that file.
- Restart `bridge.py` mid-engagement (or between `/findings/propose` calls)
  and confirm `findings.json` survived and reloads correctly on the next
  `/findings/list` call for the same engagement directory.
- Confirm a malformed `/findings/propose` (missing `title`, or an invalid
  `severity` value) returns `400`, and that in a live agent loop this
  correctly counts toward the 5-strike `agent_error` abort like any other
  malformed LLM response.
- Confirm the old IndexedDB `findings` store is gone after the `DB_VERSION`
  bump: open dev tools' IndexedDB inspector after a fresh page load, confirm
  no `findings` object store remains (only `engagement`, `steps`,
  `axis_ledger`).
